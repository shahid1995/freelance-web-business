# Custom Web Application

## Purpose

Build focused web functionality for a defined workflow, business process, or user task that a standard marketing website cannot adequately support.

## Ideal client / use case

Suitable for:

- Internal business tools
- Customer-facing workflows
- Booking/request systems
- Structured data-entry workflows
- Specialized web utilities
- Focused SaaS-style product surfaces
- Integrations that require application logic

## Core deliverables

Typical deliverables are defined per application and may include:

- Agreed user roles and workflows
- Application screens/pages
- Data model and required persistence
- Authentication/authorization when required
- Forms and validation
- Business rules explicitly included in scope
- Agreed integrations
- Error and empty states for key workflows
- Responsive behavior appropriate to the use case
- Deployment/handover material when included

## Typical scope

The project should define:

- User types
- Entry points
- Main workflows
- Required data
- Permissions
- Business rules
- External integrations
- Required notifications
- Reporting/export requirements
- Administrative capabilities

A custom application should be scoped around concrete workflows rather than an open-ended feature list.

## Boundaries / exclusions

Not included unless explicitly scoped:

- Undefined future feature backlog
- Full enterprise platform replacement
- Third-party service fees
- Unapproved data migration
- Unbounded administrative tooling
- Ongoing 24/7 operations or support
- Compliance certification or legal assurance
- Business-process consulting beyond the agreed implementation scope

## Optional extensions

- Additional user roles
- Additional workflows
- Admin tools
- Reporting/export features
- Notifications
- Approved third-party integrations
- Audit/history features
- Maintenance and incremental improvements

## Client inputs

The client should provide:

- Workflow descriptions
- User roles and permission expectations
- Business rules
- Required data fields and retention requirements
- Existing system/API documentation when applicable
- Test accounts or representative test data
- Integration credentials through approved secure channels

## Acceptance criteria

The application is complete when:

1. All agreed user roles can perform their defined workflows.
2. In-scope validation and business rules behave as specified.
3. Required data is created, read, updated, or otherwise handled as agreed.
4. Required permissions are enforced according to the approved scope.
5. Agreed integrations work under the defined test conditions.
6. Key error/empty states are handled as agreed.
7. No known critical in-scope defects remain.
8. Agreed handover documentation is provided.

The service delivers defined software behavior; it does not guarantee downstream operational or financial outcomes.
